## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| User browser → frontend JS state | User can manipulate `activeMetadataFilters` via DevTools; backend MUST re-validate every value (T-22-01 from Plan 01) |
| Frontend → ApiService → /dashboard/* | Standard authenticated JWT-bearer path; no new auth surface here |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-22-07 | T (Tampering) | activeMetadataFilters in client state | mitigate | Frontend trusts nothing — every filter value flows through the backend's org-guarded query (Plan 01 T-22-01, T-22-02). Even if a user injects a field_name for another org, the backend's `MetadataField.organization_id == current_user.organization_id` clause yields zero JOIN matches → empty result, never cross-org leakage. |
| T-22-08 | I | Cross-org information disclosure via field_id in URL | mitigate | Plan 01's GET /dashboard/metadata-fields/{id}/values returns 404 on cross-org access. Frontend never constructs a field_id manually — only uses IDs returned by GET /dashboard/metadata-fields (which is itself org-guarded). |
| T-22-09 | T | XSS via metadata field label or value rendered in chip | mitigate | Angular template binding `{{ f.fieldLabel }}: {{ f.value }}` is auto-escaped by default — never use `[innerHTML]`. Verify the chip template does not use innerHTML or DomSanitizer.bypassSecurityTrustHtml on these strings. |
| T-22-10 | D | Pathological client-side filter performance with many values | accept | Values for a single field are bounded by `DISTINCT` and stored as a single array. Realistic field cardinality is &lt; 1000 distinct values. Client-side prefix match over an array of 1000 strings is sub-millisecond. No mitigation required. |
| T-22-11 | I | Console log exposure of org metadata in browser dev tools | accept | All metadata is org-scoped; the user already has authorized access. No special handling required.
