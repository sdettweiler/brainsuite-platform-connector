**Reviewed:** 2026-05-13T00:00:00Z

## Summary

Three files were reviewed: the core scheduler (`scheduler.py`, ~2018 lines), the scheduler unit tests (`test_scheduler.py`), and the TikTok sync tests (`test_tiktok_sync.py`).

The `scoring_enabled` gate was correctly added to all four download functions. The TikTok upsert-exclusion tests are structurally sound and will catch the intended invariant against the real model. The test coverage for the scheduler gate is adequate but contains one reliability problem.

Two blockers were found: a dead-code path that silently evaluates `platform == "DV360"` inside a `not is_dv360` guard (always False — the DV360 asset queue is never populated via the non-DV360 path), and a permissive gate condition that allows downloads to proceed when `SystemConfig` is absent from the database, which is the wrong-safe direction for a feature gate. Three warnings cover a `scoring_enabled=None` edge case, a test assertion gap, and a reliability flaw in the `test_downloads_proceed_when_scoring_enabled` test.

## Critical Issues

### CR-01: Dead-code `dv360_asset_queue` assignment in every non-DV360 sync function

**File:** `backend/app/services/sync/scheduler.py:263`, `1028`, `1379`, `1704`

**Issue:** Inside the `if not is_dv360:` guard, each sync function assigns:
```python
dv360_asset_queue = result.get("_asset_queue") if platform == "DV360" else None
```
But `platform == "DV360"` (or `connection.platform == "DV360"`) is structurally impossible inside an `if not is_dv360:` block — `is_dv360` was set to `platform == "DV360"` three lines earlier. The assignment is always `None`. The outer `if dv360_asset_queue and conn_id_for_assets:` check (lines 457, 1252, 1571, 1875) therefore never fires for any non-DV360 connection, and the DV360 queue populated in the second phase (lines 403, 1173, 1509, 1826) is the only path that actually reaches `_run_dv360_asset_downloads`. This is harmless for DV360 because DV360 has its own second-phase path, but **it means the non-DV360 branch can never feed `_run_dv360_asset_downloads`**, which appears to be the original intent of the variable. If DV360 ever bypasses the two-phase split (e.g., a refactor), this silently drops asset downloads with no error. The dead branch also confuses readers into thinking there is a non-DV360 path for DV360 asset queue processing.

**Fix:** Remove the unreachable ternary and initialise the variable unconditionally to `None` before the `if not is_dv360` block (it already is `None` from the top of the function), then remove the redundant re-assignment entirely:
```python
# Before the if not is_dv360: block — dv360_asset_queue is already None from init.
# Delete these lines at 263, 1028, 1379, 1704:
# dv360_asset_queue = result.get("_asset_queue") if platform == "DV360" else None
# conn_id_for_assets = connection.id if dv360_asset_queue else None
```
The second-phase DV360 blocks already set `dv360_asset_queue` correctly (lines 403, 1173, etc.), so removal is safe.

### CR-02: `scoring_enabled` gate is permissive when `SystemConfig` row is absent

**File:** `backend/app/services/sync/scheduler.py:474`, `610`, `684`, `760`

**Issue:** All four download functions use the same gate pattern:
```python
if _system_cfg is not None and not _system_cfg.scoring_enabled:
    return  # skip downloads
```
When `SystemConfig` has no rows (`_system_cfg is None`), the condition is `False` and downloads proceed. This is the wrong-safe direction for a feature gate: if the config table is empty (fresh deploy, migration not yet run, or accidental truncation), asset downloads will run unchecked rather than fail safely. The intent documented in the comments ("if scoring is disabled, skip") implies the gate should default to *disabled*, not *enabled*, when config is unavailable.

**Fix:** Invert the None branch to default to the safe (skip) direction:
```python
# Treat missing config as scoring_enabled=False (fail-safe)
if _system_cfg is None or not _system_cfg.scoring_enabled:
    logger.info("Auto-download disabled (scoring_enabled=False or config absent); skipping downloads")
    return
```

## Warnings

### WR-01: `scoring_enabled` attribute may be `None` (nullable column), bypassing the gate

**File:** `backend/app/services/sync/scheduler.py:474`, `610`, `684`, `760`

**Issue:** `_system_cfg.scoring_enabled` is compared with `not _system_cfg.scoring_enabled`. If the column is nullable and the value is `None` (e.g., after a migration that adds the column without a default), `not None` evaluates to `True`, which means the gate fires and downloads are correctly skipped. However, if the column defaults to `False` as a nullable column with no explicit value, the truthy check `not _system_cfg.scoring_enabled` also fires correctly. The subtle risk is that `None` is being treated as equivalent to `False` (disabled) implicitly, which is the correct behavior here but is undocumented and fragile: future readers may change the nullable semantics without realising the gate behavior changes. This is distinct from CR-02 (absent row vs. present row with null value).

**Fix:** Be explicit:
```python
if not _system_cfg.scoring_enabled:  # None and False both treated as disabled
```
with a comment explaining that `None` is intentionally treated as disabled.

### WR-02: `test_downloads_skipped_when_scoring_disabled` patches `get_session_factory` incorrectly, causing the gate to never exercise the DB query

**File:** `backend/tests/services/test_scheduler.py:100`

**Issue:** The test patches `get_session_factory` to return `mock_session_factory`, where `mock_session_factory` is a `MagicMock(return_value=mock_db)`. The scheduler gate calls `get_session_factory()()` — two calls: first to get the factory callable, then to call the factory to get the async context manager. The test sets up:
```python
mock_session_factory = MagicMock(return_value=mock_db)
patch("...get_session_factory", return_value=mock_session_factory)
```
`get_session_factory` is replaced with a mock whose return value is `mock_session_factory`, so `get_session_factory()` returns `mock_session_factory`, and `get_session_factory()()` returns `mock_db` (an `AsyncMock`). This chain works — but `mock_db` is configured as `__aenter__ = AsyncMock(return_value=mock_db)`, so `async with get_session_factory()() as _gate_db:` yields `mock_db`. `mock_db.execute` returns `mock_scalar`, and `mock_scalar.scalar_one_or_none()` returns `mock_cfg` with `scoring_enabled=False`. So the gate path is exercised. The warning is that `mock_db.__aexit__` is set to `AsyncMock(return_value=False)` but the async context manager protocol requires `__aexit__` to accept `(exc_type, exc_val, exc_tb)` — the `AsyncMock` here receives those arguments correctly, but the `return_value=False` means it does not suppress exceptions, which is correct. The test is structurally valid, but `mock_db` is reused as both the context manager and the yielded value (it is its own context manager), which is unusual and fragile under refactoring. If the scheduler gate ever opens a second `get_session_factory()()` session (e.g., for a connection lookup), `mock_db.execute` would return the same `mock_scalar` with `scoring_enabled=False`, which could cause false positives.

**Fix:** Use a separate `mock_session` object as the yielded value inside the context manager, rather than making `mock_db` self-referential.

### WR-03: `test_downloads_proceed_when_scoring_enabled` swallows all exceptions, masking gate failures that crash before `create_background_job`

**File:** `backend/tests/services/test_scheduler.py:147-150`

**Issue:**
```python
try:
    await _run_meta_creatives_deferred("00000000-0000-0000-0000-000000000001", [])
except Exception:
    pass  # downstream failures OK; early return before job creation is NOT
```
If the gate is broken in a different way — e.g., it raises `AttributeError` accessing `scoring_enabled` before reaching `create_background_job` — the `except Exception: pass` swallows the crash, and `mock_create_job.call_count == 0` would cause the assertion to fail (correctly), but the failure message would not indicate *why* the job was never created. More critically, if a future refactor moves the `create_background_job` call to after an additional guard that also raises, the test would still pass while the feature is broken. The bare `except` is specifically flagged in the project's Python quality checks.

**Fix:** Narrow the exception catch to expected downstream failures, or assert the exception type:
```python
try:
    await _run_meta_creatives_deferred("00000000-0000-0000-0000-000000000001", [])
except (KeyError, AttributeError, TypeError):
    pass  # DB/connection attribute failures downstream of the gate are acceptable
# Do not catch Exception — unexpected crashes should surface
```

## Info

### IN-01: `_harmonize_with_deadlock_retry` silently returns `None` on exhausted retries instead of raising

**File:** `backend/app/services/sync/scheduler.py:40-55`

**Issue:** The retry loop returns `count, new_assets` on success, and `raise`s on non-deadlock errors or on the final deadlock attempt. However, if the loop exits normally after all retries without either returning or raising (which cannot happen as written because the `raise` on the final attempt covers the exhausted case), the function would return `None` implicitly. While the current `if not is_deadlock or attempt == MAX_DEADLOCK_RETRIES: raise` correctly re-raises on the last attempt, the absence of a final `raise` or explicit return after the loop is a latent correctness risk if the loop bounds are ever changed.

**Fix:** Add an unreachable-but-defensive `raise` after the loop:
```python
    raise RuntimeError("Deadlock retry loop exhausted without result")  # should be unreachable
```

### IN-02: `_run_dv360_asset_downloads` error output payload iterates `asset_queue.keys()` instead of `inner_queue.keys()`

**File:** `backend/app/services/sync/scheduler.py:859`, `875`

**Issue:** In the `_CookiesExpiredError` and general `Exception` handlers:
```python
"failed": [{"asset_id": str(aid), "error": "..."} for aid in asset_queue.keys()],
```
`asset_queue` is the outer dict passed to the function, which has the shape `{"queue": {...}}`. Iterating `.keys()` produces `["queue"]`, not the actual asset IDs. The Google Ads equivalent (line 579, 595) correctly uses `asset_queue.keys()` because for Google Ads `asset_queue` IS the flat `{asset_id: info}` dict. For DV360, `inner_queue = asset_queue.get("queue", {})` is the flat dict. The error payload will show `asset_id: "queue"` for all failed assets instead of real asset IDs.

**Fix:**
```python
# In both except blocks in _run_dv360_asset_downloads, replace:
"failed": [{"asset_id": str(aid), "error": "..."} for aid in asset_queue.keys()],
# with:
"failed": [{"asset_id": str(aid), "error": "..."} for aid in inner_queue.keys()],
```
Note: `inner_queue` must be declared before both try blocks, or the error handlers need a fallback. Currently `inner_queue` is declared at line 778, inside the `try:` block, so it would be out of scope in the `except _CookiesExpiredError` handler at line 825. This requires moving `inner_queue = asset_queue.get("queue", {})` to before the outer `try:`.
