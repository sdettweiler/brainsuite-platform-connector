# Phase 19.3: Close gap: Phase 15 — asset_url upsert exclusion + scoring_enabled guard - Research

**Researched:** 2026-05-13
**Domain:** TikTok sync upsert exclusion list + platform-wide asset download gating
**Confidence:** HIGH

## Summary

Phase 19.3 closes two confirmed tech debt items from the v1.3 milestone audit (2026-05-13):

1. **Upsert exclusion gap:** `asset_url` and `video_source_url` are NOT in the `_upsert_records` ON CONFLICT exclusion list for TikTok raw table upserts. During a re-sync, the upsert operation can temporarily null these fields in the DB even though the S3 file is preserved. Fix: add these URL fields to the ON CONFLICT DO UPDATE SET exclusion list so already-populated URL fields are not overwritten with NULL on re-sync.

2. **scoring_enabled gate gap:** Asset download proceeds regardless of `SystemConfig.scoring_enabled` toggle across all platforms (Meta, TikTok, Google Ads, DV360). The gate currently exists only at the scoring level (in `scoring_job.py:68`), not at the download orchestration level. Fix: check `SystemConfig.scoring_enabled` before initiating any asset download.

**Primary recommendation:** 
- Add `asset_url` and `video_source_url` to TikTok's `_upsert_records` ON CONFLICT exclusion set (1-line fix in upsert statement).
- Add `SystemConfig.scoring_enabled` guard at download entry points in all 4 platform handlers (`_run_*_asset_downloads` functions in scheduler.py) before job creation.

### Pattern 1: ON CONFLICT DO UPDATE Exclusion List

**What:** SQLAlchemy's `on_conflict_do_update()` with `excluded=` parameter to preserve already-populated fields during re-sync.

**When to use:** Any upsert operation where a field may be null in the incoming data but already populated in the DB (e.g., S3 URLs cached from a prior sync).

**Current state (TikTok):**
```python
# tiktok_sync.py:360–368
stmt = stmt.on_conflict_do_update(
    constraint="uq_tiktok_daily_ad",
    set_=update_cols,  # update_cols built ~50 lines above
)
```

The `update_cols` dict does NOT exclude `asset_url` or `video_source_url`. During re-sync, if TikTok API doesn't return these fields (or returns null), they get nulled in the DB despite the S3 file existing.

**Fix:**
```python
# Build exclusion list — fields that should NOT be updated if they're already set
excluded_cols = {"asset_url", "video_source_url"}
# When building update_cols, skip these fields OR explicitly exclude them:
set_ = {k: v for k, v in update_cols.items() if k not in excluded_cols}
# OR use SQLAlchemy excluded (available in v1.4+):
# set_ = {col: excluded(col) for col in excluded_cols}  # keep existing value
stmt = stmt.on_conflict_do_update(
    constraint="uq_tiktok_daily_ad",
    set_=set_,
)
```

**Cross-platform note:** Meta and Google Ads may have similar patterns. Research found no direct calls to `on_conflict_do_update` in those files during this search, suggesting they may use different upsert syntax or not have the same null window.

### Pattern 2: SystemConfig.scoring_enabled Guard at Download Entry Point

**What:** Check `SystemConfig.scoring_enabled` before calling `_run_*_asset_downloads()` in scheduler.py.

**When to use:** Any operation triggered by auto-sync that should respect the SuperAdmin's "disable auto-scoring" toggle (which implicitly means "disable auto-download" to avoid wasted storage).

**Current state:**
- `scoring_job.py:68` checks `SystemConfig.scoring_enabled` before scoring a batch
- `download_assets_post_commit()` methods in all 4 sync services are called unconditionally after `_enrich_from_ad_get()` or equivalent
- Scheduler.py calls `_run_*_asset_downloads()` without checking the gate

**Fix location (scheduler.py):**
```python
# Before any _run_*_asset_downloads call, check:
from app.models.system_config import SystemConfig
from sqlalchemy import select

async def _run_tiktok_asset_downloads(connection_id, asset_queue: dict) -> None:
    # Add at function start:
    async with get_session_factory()() as db:
        system_cfg = (await db.execute(select(SystemConfig).limit(1))).scalar_one_or_none()
        if system_cfg and not system_cfg.scoring_enabled:
            logger.info("Auto-download disabled (scoring_enabled=False); skipping TikTok asset downloads")
            return
    # ... rest of function
```

Repeat for `_run_meta_asset_downloads`, `_run_google_ads_asset_downloads`, `_run_dv360_asset_downloads`.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Upsert conflict resolution | Custom merge logic in Python | SQLAlchemy `on_conflict_do_update()` with constraint + exclusion set | DB-level atomicity; prevents race conditions during concurrent syncs |
| Auto-download gating | Env var or hardcoded flag | `SystemConfig.scoring_enabled` from DB | Single source of truth; SuperAdmin can toggle at runtime without redeployment |
| Asset URL preservation | Manual "if not null then update else skip" checks | ON CONFLICT exclusion list | Simpler, atomic, no race windows |

**Key insight:** The null window during re-sync is a classic race condition if handled in application logic. DB-level constraints are the correct place for upsert semantics.

## Common Pitfalls

### Pitfall 1: Forgetting to Exclude All URL Fields

**What goes wrong:** Add `asset_url` to exclusion but miss `video_source_url`, or vice versa. One field gets nulled, the other is preserved, leading to inconsistent state.

**Why it happens:** Multiple URL field names across the schema (asset_url, creative_asset_url, video_source_url, media_asset_url); easy to miss one.

**How to avoid:** 
- Audit TikTokRawPerformance model to find ALL URL fields that store S3 download results
- Add comprehensive comment in code listing all excluded fields and why
- Add a unit test that verifies both fields are in the exclusion set

**Warning signs:** 
- Harmonizer.py still gets null asset_url on re-sync for some creatives
- CreativeAsset.asset_url or CreativeAsset.video_url still null after sync despite S3 file existing

### Pitfall 2: Checking scoring_enabled at Wrong Level

**What goes wrong:** Check only in scoring_job.py (already done) but not at download entry. Downloads proceed unconditionally, wasting storage for disabled orgs.

**Why it happens:** Download gate was added in Phase 15 without considering the disable-scoring use case; scoring gate was added in Phase 17 for scoring specifically.

**How to avoid:**
- Check scheduler.py — confirm all 4 `_run_*_asset_downloads()` functions query SystemConfig.scoring_enabled before proceeding
- Document in code that auto-download is tied to auto-scoring: "download gate mirrors scoring gate"
- Add test: when scoring_enabled=False, verify no download jobs are created

**Warning signs:**
- SuperAdmin disables scoring_enabled; assets still download; storage grows
- Download job created in DB for disabled org; scoring job skipped (inconsistent)

### Pitfall 3: Assuming All Platforms Have Same Download Architecture

**What goes wrong:** Add gate to TikTok only, forget Meta/Google Ads/DV360. Inconsistent behavior across platforms.

**Why it happens:** Each platform has different sync service (tiktok_sync.py, meta_sync.py, etc.); easy to miss one.

**How to avoid:**
- Grep: `_run_.*_asset_downloads` in scheduler.py — should find exactly 4 functions (one per platform)
- Verify each one calls the download helper and is reachable from sync completion
- Add test: disable scoring_enabled, trigger sync on all 4 platforms, verify zero download jobs created

**Warning signs:**
- TikTok downloads skip when disabled, but Meta downloads proceed
- Different platform behavior during SuperAdmin toggle
