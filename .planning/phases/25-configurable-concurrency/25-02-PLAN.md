<objective>
Wrap the existing Phase 24 `_do_download` call sites in DV360 and Google Ads sync services with `async with semaphore:`, and expose GET/PUT `/super-admin/download-concurrency` endpoints so the admin UI (Plan 25-03) can read and write the setting.

Purpose: This plan is the enforcement + control plane. After Plan 25-01 establishes the storage + cache, this plan (a) makes every download actually respect the semaphore and (b) gives the SuperAdmin an API to tune the limit.

Output:
- DV360 and Google Ads download paths acquire a Semaphore slot before invoking `_do_download` and release it on retry-loop exit (success or exception)
- `GET /api/v1/super-admin/download-concurrency` → `ConcurrencyConfigResponse{max_concurrent_downloads: int}`
- `PUT /api/v1/super-admin/download-concurrency` with `ConcurrencyConfigRequest{max_concurrent_downloads: int}` validated `1 <= N <= 10` → updates SystemConfig, returns fresh `ConcurrencyConfigResponse`
- Pydantic-level validation ensures DB never receives an out-of-range value
- Tests in `test_super_admin_proxy.py` (existing file in the same SuperAdmin tests cluster) cover GET default-3, PUT happy path, PUT 422 on out-of-range, 403 on non-SuperAdmin
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Browser → API | SuperAdmin sends `{max_concurrent_downloads: N}` via PUT — untrusted integer input crosses here |
| API → DB | Validated payload is written via SQLAlchemy ORM |
| Download caller → semaphore | Every coroutine wanting to call `_do_download` MUST go through `async with semaphore:` — no bypass path exists |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-25-06 | Tampering | PUT `/download-concurrency` with out-of-range integer (0, 11, -100, MAX_INT) | mitigate | Pydantic `Field(ge=1, le=10)` rejects with HTTP 422 BEFORE the handler body executes — DB is never reached. Tested explicitly. |
| T-25-07 | Spoofing / Elevation of Privilege | Non-SuperAdmin calling `/download-concurrency` GET or PUT | mitigate | `Depends(get_current_superadmin)` on both handlers — identical guard pattern as every other endpoint in `super_admin.py`. | T-25-08 | Denial of Service | Adversary sets `max_concurrent_downloads = 1` to throttle production | accept | Mitigated by SuperAdmin-only access (T-25-07). | T-25-09 | Denial of Service | Download semaphore not actually enforced because `_do_download` runs blocking I/O | accept | Per RESEARCH.md Pitfall 3: `_do_download` uses `loop.run_in_executor(None, download_sync)` which yields to the event loop — semaphore IS enforced. Phase 24 already established this pattern; this plan does not change it. |
| T-25-10 | Tampering | Download caller bypasses semaphore by importing `_do_download` directly and calling it without `async with` | mitigate | Both call sites (DV360 + Google Ads) are now wrapped; `_do_download` is a CLOSURE defined inside the wrapping method, not a module-level export — it cannot be imported from outside.
