## Warnings

### WR-01: Stale closed EventSource reference left on null-token early return

**File:** `frontend/src/app/core/services/job-monitor.service.ts:41-48`

**Issue:** When `connect()` takes the null-token early return, `this.eventSource?.close()` correctly closes the old connection, but `this.eventSource` is never set to `null`. The field continues to hold a reference to the now-closed `EventSource` object. `disconnect()` — called from `ngOnDestroy` (component line 70) — will subsequently call `.close()` on the dead object again (harmless for the browser, but semantically incorrect). More importantly, any code that checks `if (this.eventSource !== null)` as a liveness proxy will produce a false positive: the service appears connected when it is not.

Compare with `disconnect()` (line 76-77), which correctly does both steps: `this.eventSource?.close(); this.eventSource = null;`.

**Fix:**
```typescript
connect(): void {
  this.eventSource?.close();
  this.eventSource = null;          // <-- add this line

  const token = this.authService.getAccessToken();
  if (!token) {
    this.statusSubject.next('disconnected');
    return;
  }
  // ... rest unchanged
}
```

### WR-02: Uncaught JSON.parse in job_update listener can crash the Angular zone

**File:** `frontend/src/app/core/services/job-monitor.service.ts:58`

**Issue:** `JSON.parse(event.data)` is called without a try/catch inside `this.ngZone.run()`. If the backend emits a malformed SSE payload (truncated frame, empty data, non-JSON debug message), the parse throws an uncaught exception inside the Angular zone. Angular's default error handler will log to the console and re-throw, but the `job_update` listener remains attached and the service continues attempting to parse future events — meaning one bad frame can leave the UI in a partially updated state with no visible error.

**Fix:**
```typescript
this.eventSource.addEventListener('job_update', (event: MessageEvent) => {
  this.ngZone.run(() => {
    try {
      const job: JobSnapshot = JSON.parse(event.data);
      this.jobMap.set(job.job_id, job);
      this.jobsSubject.next(Array.from(this.jobMap.values()));
    } catch {
      // Malformed SSE frame — discard silently; connection remains open.
    }
  });
});
```

### WR-03: getJobs() appends jobType and status to the URL without encoding

**File:** `frontend/src/app/core/services/job-monitor.service.ts:87-88`

**Issue:** `getJobs()` constructs the query string by direct string interpolation:

```typescript
if (jobType) { path += `&job_type=${jobType}`; }
if (status)  { path += `&status=${status}`; }
```

`clearJobs()` on line 97 correctly uses `encodeURIComponent()` for both parameters, but `getJobs()` does not. If a caller ever passes a `jobType` or `status` value containing `&`, `=`, `+`, or spaces (e.g., a composite status label), the resulting URL will be misinterpreted by the server. The inconsistency also makes it easy for future callers to assume encoding is handled uniformly when it is not.

**Fix:**
```typescript
if (jobType) { path += `&job_type=${encodeURIComponent(jobType)}`; }
if (status)  { path += `&status=${encodeURIComponent(status)}`; }
```

## Info

### IN-01: onerror handler caps retries but never re-initiates reconnection

**File:** `frontend/src/app/core/services/job-monitor.service.ts:69-72`

**Issue:** After three consecutive `onerror` firings the status becomes `disconnected`, but the handler never calls `connect()` to attempt a fresh connection. The browser's native EventSource retry behaviour is still active (it will keep reconnecting at its own cadence), but `reconnectAttempts` will continue incrementing beyond 3 without any application-level reconnect logic. This means the UI can show `disconnected` permanently even after the backend recovers, until the component is destroyed and re-created or the user navigates away and back.

This is a pre-existing design gap, not introduced by phase 19.1, and is noted here for awareness only.

**Fix (suggestion):** After emitting `disconnected`, call `this.disconnect()` to halt the browser's automatic retry loop and surface a user-visible "reconnect" action, or schedule a single application-level reconnect after a back-off delay. Either is preferable to the current state where the browser retries silently while the UI shows a permanent disconnect badge.
