# Phase 19.1: Close Gap BLOCKER-02 + BLOCKER-03 — Research

**Researched:** 2026-05-13
**Domain:** Angular SSE service (job-monitor.service.ts), Angular route guard chain, EventSource lifecycle
**Confidence:** HIGH — all findings are based on direct codebase inspection of the three files at issue

---

## Summary

Both blockers are isolated to `job-monitor.service.ts` and require surgical changes to `connect()` only. The null-token race (BLOCKER-02) is real but narrower than the audit implies: `authGuard` guarantees a valid token exists before any protected route component mounts, so the primary null window is NOT on normal page load — it is on `clearJobs()` reconnect after token expiry, and in the missing `reconnectAttempts` reset between connect() calls. The EventSource leak (BLOCKER-03) is unconditional: any second call to `connect()` opens a new `EventSource` on top of the old one. Three lines added to the start of `connect()` fix both blockers. No component changes are needed.

**Primary recommendation:** Add `this.eventSource?.close()`, a null-guard on `token`, and a `this.reconnectAttempts = 0` reset at the start of `connect()`. Total change: 4 lines.

## Token Timing Analysis

### AuthService internals

`AuthService.accessToken$` is a `BehaviorSubject<string | null>` initialised to `null`.
It is set to a real JWT by exactly two code paths [VERIFIED: auth.service.ts lines 66-68, 91-93]:
- `login()` → `tap(res => this.accessToken$.next(res.access_token))`
- `refreshTokens()` → `tap(res => this.accessToken$.next(res.access_token))`

`getAccessToken()` returns `this.accessToken$.value` — a synchronous snapshot [VERIFIED: auth.service.ts line 57-59]. It returns `null` if neither `login()` nor `refreshTokens()` has completed.

### Route guard chain before ngOnInit

The `/configuration/jobs` route is protected by two guards in sequence [VERIFIED: app.routes.ts, configuration.routes.ts]:

1. `authGuard` (app level, `canActivate` on the root shell) — fires for every protected child route. If `auth.isAuthenticated` is false (i.e. `accessToken$.value === null`), it calls `auth.refreshTokens()` and waits for the Observable to complete before allowing navigation. This guarantees `accessToken$.value` is non-null before any child component's constructor or `ngOnInit` runs [VERIFIED: auth.guard.ts lines 11-19].

2. `IsSuperAdminGuard` (configuration child, `canActivate` on the `jobs` path) — checks `currentUser?.is_superuser`. If not cached, calls `loadCurrentUser()` (GET /auth/me). Does NOT call `refreshTokens()`. By the time this runs, `authGuard` has already set the token [VERIFIED: is-superadmin.guard.ts lines 14-30].

### Conclusion on token availability at ngOnInit

**Token IS guaranteed non-null at the point ngOnInit fires for `JobMonitorComponent`** under the normal navigation path. `authGuard` completes a successful `refreshTokens()` before Angular resolves the route and mounts the component. [VERIFIED: guard chain]

### When null IS possible

| Scenario | Why token is null | Realistic? |
|----------|------------------|-----------|
| Token expires while user is on the page | `accessToken$.value` is a snapshot from the last refresh; no background refresh exists | Yes — long-lived sessions |
| `clearJobs()` calls `connect()` after a transient 401 cycle | Same as above; token may have expired between page load and the clear action | Yes |
| EventSource `onerror` triggers after 401 from expired token | `reconnectAttempts` reaches 3; subsequent re-entry to `connect()` via the error handler (not present — onerror does NOT call connect()) | N/A — no auto-reconnect in code |
| Dev/test scenario: component instantiated without guard | Token starts null | Possible in unit tests |

**The audit's claim that token is null "before token hydration" is slightly misleading** — the normal page load does NOT have this problem because `authGuard` runs first. The real risks are: (a) token expiry between page load and reconnect after `clearJobs()`; (b) missing `reconnectAttempts` reset causing false disconnected state even when a fresh token is valid.

### Does the null guard alone suffice?

**No — a bare null-guard is necessary but not sufficient.** There are two related bugs:

1. `reconnectAttempts` is never reset at the start of `connect()`. If a prior error cycle incremented it to 3, the very first `onerror` on the next `connect()` call will immediately emit `'disconnected'` (because `reconnectAttempts` is already `>= 3` after the increment).

2. The null-guard should emit `'reconnecting'` (not `'disconnected'`) if it fires during a clearJobs reconnect, to allow future retries. But since no auto-retry loop exists in the service, emitting `'disconnected'` is the correct terminal state — consistent with what three onerror cycles would produce. This matches the audit's proposed fix.

## BLOCKER-02 Fix: Null Token Race

### Exact implementation

Add at the **start** of `connect()`, before the URL is built:

```typescript
connect(): void {
  // BLOCKER-02: guard against null token (e.g. after token expiry or guard bypass)
  const token = this.authService.getAccessToken();
  if (!token) {
    this.statusSubject.next('disconnected');
    return;
  }
  // BLOCKER-02: reset reconnect counter so fresh connect() starts clean
  this.reconnectAttempts = 0;

  const url = `/api/v1/jobs/stream?token=${token}`;
  // ... rest of existing code unchanged
```

### Why `reconnectAttempts = 0` must be added here

Without the reset, this sequence produces permanent `'disconnected'` even with a valid token:

1. User opens page. Token valid. `connect()` runs. EventSource opens.
2. Token expires after 30 minutes. Server closes SSE connection.
3. `onerror` fires. `reconnectAttempts` → 1, status = `'reconnecting'`.
4. `onerror` fires again (browser retries). `reconnectAttempts` → 2, status = `'reconnecting'`.
5. `onerror` fires a third time. `reconnectAttempts` → 3, status = `'disconnected'`.
6. User clicks "Clear completed jobs". `clearJobs()` fires. On success, calls `connect()` with a fresh valid token.
7. Without the reset: `reconnectAttempts` is still 3. The very first `onerror` on the new EventSource would push `reconnectAttempts` to 4, which is `>= 3`, so status immediately becomes `'disconnected'` again — even though the token is valid.
8. With the reset: `reconnectAttempts` = 0 at start of `connect()`. Three `onerror` events are needed before the service gives up.

[VERIFIED: job-monitor.service.ts lines 26, 30, 51-59 — `reconnectAttempts` is a class field with no reset mechanism between connect() calls]

## BLOCKER-03 Fix: EventSource Leak

### Exact implementation

Add at the **start** of `connect()`, before the null-guard:

```typescript
connect(): void {
  // BLOCKER-03: close any existing EventSource before opening a new one
  this.eventSource?.close();

  // BLOCKER-02: guard against null token
  const token = this.authService.getAccessToken();
  // ...
```

### Why close-before-open is safe in all call scenarios

- **First call (ngOnInit):** `this.eventSource` is `null` (initial class field value). `null?.close()` is a no-op. Safe.
- **After clearJobs() reconnect:** `disconnect()` has NOT been called before `connect()` in this flow. `this.eventSource` points to the old (now-closed-by-server) EventSource. Calling `.close()` on an already-server-closed EventSource is safe — the DOM EventSource `close()` method is idempotent [ASSUMED — standard browser EventSource API behaviour; no Context7 verification available for browser APIs].
- **After disconnect():** `disconnect()` calls `this.eventSource?.close(); this.eventSource = null`. So `this.eventSource` is already `null`. The `?.close()` at the start of `connect()` is a no-op. Safe.
- **Hypothetical rapid double-connect:** First call closes nothing (null). Second call closes the EventSource created by the first call. Exactly one active connection remains. Correct.

### Server-side impact

Each unclosed `EventSource` holds a live server-side generator running the `sse_generator` coroutine loop and a dedicated Redis pubsub subscription (`sse:job_updates`). The `finally` block in `sse_generator` calls `pubsub.unsubscribe` + `pubsub.close` on disconnect detection. Browser `EventSource.close()` triggers the ASGI disconnect signal, which `request.is_disconnected()` detects at the next poll cycle (within ~5 seconds, governed by `_PUBSUB_POLL_TIMEOUT_SECONDS = 5.0`). So `.close()` on the frontend reliably frees the server-side subscription within ~5 seconds [VERIFIED: jobs.py lines 104-161].

## Reconnect Loop Analysis

### Current reconnect behaviour

There is NO explicit reconnect timer loop in `job-monitor.service.ts`. The browser's `EventSource` performs its own automatic reconnect (browser-native, approximately every 3 seconds by default). Each browser reconnect attempt triggers `onerror` on failure, which increments `reconnectAttempts`. On the third failure, the service emits `'disconnected'` and stops updating status.

The service does NOT call `connect()` from inside `onerror`. Recovery requires either:
- A user action that calls `connect()` explicitly (currently: `clearJobs()`)
- A page reload

### After the fix

With `reconnectAttempts = 0` reset at start of `connect()`:

- Fresh `connect()` → token valid → EventSource opens → `onopen` fires → `reconnectAttempts = 0`, status = `'live'`. Correct.
- Fresh `connect()` → token valid → server returns 401 (expired token) → `onerror` fires 3 times → status = `'disconnected'`. User is correctly informed SSE failed.
- Fresh `connect()` → token valid → transient network blip → one `onerror`, `reconnectAttempts = 1`, status = `'reconnecting'` → browser auto-retries → `onopen` fires → `reconnectAttempts = 0`, status = `'live'`. Correct recovery.
- `clearJobs()` succeeds → `connect()` called → `reconnectAttempts` reset to 0 → new EventSource opens cleanly. Correct.

### Edge cases after fix

| Scenario | Behaviour | Correct? |
|----------|-----------|---------|
| Token null at connect() | Guard returns early, emits 'disconnected', no EventSource opened | Yes |
| clearJobs() → connect() with expired token | 3 onerror cycles → 'disconnected'. User must reload. | Acceptable |
| ngOnInit connect() → multiple onerror → clearJobs() connect() | reconnectAttempts resets to 0, fresh error budget for new connection | Yes — fix required |
| Rapid double clearJobs() | Second connect() closes first EventSource immediately | Yes |

## Implementation Notes

### The `reconnectAttempts` reset is REQUIRED, not optional

The audit's proposed fix omits the `reconnectAttempts = 0` reset. Without it, BLOCKER-02 is only partially fixed: the literal `?token=null` string is prevented, but a user who experiences a 3-onerror cycle from token expiry (step 5 in the scenario above) and then triggers `clearJobs()` will still see permanent `'disconnected'` on the new connection's first error, because `reconnectAttempts` carries over.

### Ordering of the three changes

The correct order inside `connect()` is:

```
1. this.eventSource?.close();          // BLOCKER-03 — close before open
2. const token = getAccessToken();      // BLOCKER-02 — read token
3. if (!token) { emit disconnected; return; }  // BLOCKER-02 — null guard
4. this.reconnectAttempts = 0;         // fix reconnect counter state
5. const url = ...token...;            // existing URL build
6. this.eventSource = new EventSource(url);  // existing open
```

This order is important: close-before-open must happen before the null guard, so that if we return early due to null token, we still clean up the old EventSource first. If we return early before closing, the old EventSource leaks on null-token-guard-exit.

### No Observable subscription needed

The phase description raises the question of whether an `Observable<string>` subscription is needed instead of the one-shot getter. Based on the guard chain analysis: **no**. `authGuard` ensures the token is available at `ngOnInit`. The null guard is a safety net for the `clearJobs()` reconnect and token-expiry scenarios, where a synchronous check + early return is the correct pattern — subscribing to `accessToken$` and deferring the connect until non-null would require managing additional subscriptions and lifecycle complexity that is not warranted by the failure modes.

### `reconnectAttempts` never resets at `onopen` in the current code

Wait — actually `onopen` does reset `reconnectAttempts` [VERIFIED: job-monitor.service.ts line 52: `this.reconnectAttempts = 0`]. So `onopen` correctly resets the counter when a connection succeeds. The problem is only that there is no reset at the start of `connect()` before the new EventSource is even opened — meaning the counter carries over from a previous failed session into the new session's error budget.
