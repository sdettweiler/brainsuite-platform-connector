Existing _process_asset structure (scoring_job.py L304-544):
```
_process_asset(score_id, asset, endpoint_type):
  try:
    # Load org config (session)
    # Load brainsuite_app (same session)
    # Guard: incomplete config → _mark_unscored, return
    # Guard: mandatory fields → _mark_unscored, return
    # Download file bytes (no session)
    # Load metadata_dict (session)
    # submit_job_with_upload → job_id  (HTTP)
    # Update score_row.brainsuite_job_id (session)
    # poll_job_status → result_data (HTTP)
    # persist_and_replace_visualizations → stored_output
    # extract_score_data → score_data
    # Update score_row COMPLETE (session)
  except BrainSuiteJobError:
    _mark_failed(score_id, ...)
  except Exception:
    _mark_failed(score_id, ...)
```

BackgroundJob create goes at the TOP of _process_asset (before the try block),
immediately after `asset_id = asset.id`. This ensures bg_job_id is accessible in
all except handlers.

The BackgroundJob tracks only the scoreable path. Guard paths (_mark_unscored)
do NOT create BackgroundJobs — they represent "skipped" assets, not "failed" jobs.
Only the try block starting at config load creates a BackgroundJob.

Rationale: Creating a BackgroundJob for skipped assets would pollute the monitoring
dashboard with entries that have no meaningful progress or outcome. The INSTR-04
requirement specifies "scoring runs" — skipped assets are not scoring runs.

platform_connection_id for scoring (D-07): `asset.platform_connection_id`
(PlatformConnection FK already on CreativeAsset — available without extra DB query).
If None (e.g., orphaned asset), pass None to create_background_job per D-07.
