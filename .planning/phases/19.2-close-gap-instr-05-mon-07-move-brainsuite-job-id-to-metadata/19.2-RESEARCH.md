# Phase 19.2: Close gap: INSTR-05/MON-07 - Research

**Researched:** 2026-05-13
**Domain:** Job metadata routing and References panel display  
**Confidence:** HIGH

## Summary

Phase 19.2 closes two partial gaps from the v1.3 milestone audit:

1. **INSTR-05 Partial** — `brainsuite_job_id` for scoring jobs is currently stored in the `output` JSONB column (line 561 of `scoring_job.py`), not the `metadata_` column. The frontend References panel only reads `metadata_` (line 234–238 of `job-detail-panel.component.ts`); therefore the `brainsuite_job_id` is never displayed in the References header for scoring jobs. **Fix:** Store `brainsuite_job_id` in `metadata_` during scoring instrumentation.

2. **MON-07 Partial** — `platform_sync_run_id` is declared in `KNOWN_EXTERNAL_ID_KEYS` in the frontend (line 39 of `job-detail-panel.component.ts`) but is never populated by any backend `create_background_job()` call. It shows as a References row with an empty value. **Fix:** Remove it from `KNOWN_EXTERNAL_ID_KEYS`.

The phase is straightforward: two code edits in the backend (add `brainsuite_job_id` to metadata dict on scoring completion) and one edit in the frontend (drop orphaned key from constant). No database migration or test rewrites required — metadata_ already exists and is mutable for new records.

**Primary recommendation:** (1) Add `metadata` parameter to `update_background_job()` in `job_tracker.py` that merges the passed dict into `job.metadata_` using `{**(job.metadata_ or {}), **metadata}`. (2) In `scoring_job.py`, AFTER the BrainSuite API call returns `job_id` (around line 514, after committing `score_row.brainsuite_job_id`), call `await update_background_job(bg_job_id, metadata={"brainsuite_job_id": str(job_id)})`. NOTE: brainsuite_job_id is NOT available at `create_background_job()` call time (line 409) — it can only be written after the BrainSuite API returns. Do NOT modify the existing COMPLETE update call; keep `"brainsuite_job_id"` in the output dict for backward compat. (3) Remove `'platform_sync_run_id'` from `KNOWN_EXTERNAL_ID_KEYS` in `job-detail-panel.component.ts` line 39.

## Common Pitfalls

### Pitfall 1: Overwriting metadata_ on update

**What goes wrong:** After calling `create_background_job()` with initial metadata dict (asset_id, creative_score_result_id), you might attempt to UPDATE the metadata_ column to add brainsuite_job_id. SQLAlchemy's conditional update logic can accidentally null the dict if not careful.

**Why it happens:** The `update_background_job()` helper (line 70–121 in job_tracker.py) sets fields only if the parameter is non-None. If you call `update_background_job(job_id, status="RUNNING")` without passing metadata, it won't touch the existing dict. But if you call it with `metadata=None`, you risk clearing it.

**How to avoid:** Add `brainsuite_job_id` to the initial metadata dict at `create_background_job()` call time (line 409–412 in scoring_job.py) BEFORE the BrainSuite API call. Once the job_id is returned, store it in the CreativeScoreResult row (line 511), but do NOT update BackgroundJob.metadata_ again. The metadata_ dict is set once and left alone.

**Warning signs:** 
- In tests: metadata_ column is empty `{}` after scoring completes (should contain asset_id, creative_score_result_id, brainsuite_job_id)
- In production: References panel shows no brainsuite_job_id for any scoring job (when it should show for all)

### Pitfall 2: Confusing metadata_ with output

**What goes wrong:** The audit finding says "brainsuite_job_id for scoring jobs stored in output not metadata_". A developer might misread this as "brainsuite_job_id should be in output" and leave it there, missing the point that the References panel ONLY reads metadata_.

**Why it happens:** Both columns are JSONB; both store job-related dicts. The distinction is:
- `metadata_` = cross-reference keys (sync_job_id, asset_id, creative_score_result_id, brainsuite_job_id) — human-facing IDs for tracing
- `output` = job-type-specific results (score, dimensions, downloaded[], failed[]) — machine-readable results

**How to avoid:** Check the getExternalIds() function in the frontend (line 234–238): it reads from `jobDetail.metadata_`, not output. If it's not in metadata_, it won't be displayed in References. Test this by submitting a scoring job and verifying the References panel shows brainsuite_job_id.

**Warning signs:**
- Frontend References panel shows no brainsuite_job_id despite the backend storing it
- Test assertion for MON-07 fails: "References panel should display brainsuite_job_id"

### Pitfall 3: Forgetting to remove platform_sync_run_id from the frontend

**What goes wrong:** You add brainsuite_job_id to metadata_ and update the backend, but leave platform_sync_run_id in KNOWN_EXTERNAL_ID_KEYS. The References panel now displays an empty row for platform_sync_run_id (since no backend call ever populates it).

**Why it happens:** KNOWN_EXTERNAL_ID_KEYS is a frontend constant that acts as a whitelist. If a key is in the whitelist but never set by the backend, getExternalIds() filters it out (line 236: `.filter(k => ... [k])`), which silently omits empty values. But the intention is to remove platform_sync_run_id entirely, not leave it as a silent filter.

**How to avoid:** Remove `'platform_sync_run_id'` from KNOWN_EXTERNAL_ID_KEYS as part of Phase 19.2. Search the entire codebase (backend and frontend) to confirm no other code references platform_sync_run_id — it should not be set anywhere.

**Warning signs:**
- Grep search finds "platform_sync_run_id" in any file other than RESEARCH.md / ROADMAP.md
- References panel displays a row with blank value (should only display populated keys)
