**Reviewed:** 2026-05-13
**Depth:** standard

## Summary

This phase adds `brainsuite_job_id` to `BackgroundJob.metadata_` after a BrainSuite scoring job is submitted, so the job detail panel can display the external ID in its References section. The change touches three files: `job_tracker.py` (the metadata merge helper), `scoring_job.py` (the new metadata update call), and the Angular `JobDetailPanelComponent` (the `getExternalIds()` display path). A test file exercises INSTR-04/INSTR-05.

One critical bug was found: the metadata merge in `update_background_job` silently discards the in-memory dict spread when SQLAlchemy does not detect a JSONB column mutation, meaning `brainsuite_job_id` may never actually be persisted to the database — the core deliverable of this phase. Several quality and robustness warnings round out the findings.

## Critical Issues

### CR-01: JSONB metadata merge is silently dropped — `brainsuite_job_id` may never persist

**File:** `backend/app/services/sync/job_tracker.py:115`

**Issue:** `job.metadata_ = {**(job.metadata_ or {}), **metadata}` creates a new Python dict and assigns it to `job.metadata_`. SQLAlchemy tracks changes to mapped attributes by identity comparison. Because `JSONB` columns are mapped as plain `dict` (no `MutableDict.as_mutable()` extension and no `flag_modified` call), SQLAlchemy may or may not detect this reassignment as a "dirty" change depending on the session's change-tracking state. When the object was freshly loaded in the same session the assignment is typically detected, but SQLAlchemy's JSONB mutation tracking is unreliable without `MutableDict` — there is no guarantee the `UPDATE` is emitted, especially across minor SQLAlchemy version changes or when the column default is `{}` (falsy equality comparison edge cases). The same risk applies to `job.output` and `job.error` JSONB columns in the same function.

This is the central deliverable of Phase 19.2: if the UPDATE is silently dropped, `brainsuite_job_id` is never written to `background_jobs.metadata` and the References panel in the frontend will always be empty for scoring jobs.

**Fix:** Add `flag_modified` after any JSONB column reassignment, or use `MutableDict.as_mutable(JSONB)` on the model columns:

Option A — minimal, per-call fix in `update_background_job`:
```python
from sqlalchemy.orm.attributes import flag_modified

if metadata is not None:
    job.metadata_ = {**(job.metadata_ or {}), **metadata}
    flag_modified(job, "metadata_")

if output is not None:
    job.output = output
    flag_modified(job, "output")

if error is not None:
    job.error = error
    flag_modified(job, "error")
```

Option B — model-level fix in `backend/app/models/jobs.py` (preferred, covers all callers):
```python
from sqlalchemy.ext.mutable import MutableDict
from sqlalchemy.dialects.postgresql import JSONB

output:    Mapped[dict] = mapped_column(MutableDict.as_mutable(JSONB), default=dict)
metadata_: Mapped[dict] = mapped_column("metadata", MutableDict.as_mutable(JSONB), default=dict)
error:     Mapped[dict] = mapped_column(MutableDict.as_mutable(JSONB), nullable=True)
```

## Warnings

### WR-01: `score_asset_now` leaves `expunge_all` outside the `async with` block — detached object risk

**File:** `backend/app/services/sync/scoring_job.py:238-248`

**Issue:** The `db.expunge_all()` call at line 246 is inside the `async with` block (correct), but the guard that checks `if row:` at line 245 calls `db.expunge_all()` conditionally. If `row` is `None`, `expunge_all` is never called, which is fine — but the asymmetry means the comment at line 246 ("detach while attributes are still loaded") is misleading: `expunge_all` is only called on the success path. More importantly, the `row` variable itself (a `Row` tuple from `result.one_or_none()`) is not an ORM-mapped object — it is a SQLAlchemy `Row` containing two mapped instances. Calling `db.expunge_all()` expunges all objects tracked by the session, including the two model instances inside the row tuple. After the `async with` block closes the session, accessing `score_row.endpoint_type` at line 278 and `asset.*` attributes throughout `_process_asset` will succeed only if the detach happened before the session closed (which it did), but the pattern is fragile: if the expunge order or session close order changes, you get `DetachedInstanceError`. The batch path at line 167 has the same pattern but is more defensible since `expunge_all` is unconditional there.

**Fix:** Explicitly expunge only after confirming `row` is not None, or use `make_transient` per object; and add a comment clarifying that `row` itself is a `Row` tuple, not a model instance:
```python
if row:
    score_row, asset = row
    db.expunge(score_row)
    db.expunge(asset)
```

### WR-02: `get_external_ids()` uses a falsy filter — numeric zero and `false` external IDs are silently dropped

**File:** `frontend/src/app/features/configuration/pages/job-monitor/job-detail-panel/job-detail-panel.component.ts:236`

**Issue:** `.filter(k => (this.jobDetail!.metadata_ as any)[k])` uses a truthy check. If a metadata value is `0`, `false`, or `""`, the key is suppressed. For `brainsuite_job_id` (always a non-empty string UUID) this is safe today, but `sync_job_id` values from older sync jobs could conceivably be stored as `null` due to a schema migration gap. More importantly, the filter silently hides an entry rather than showing a placeholder — the developer will see nothing and assume the key was never written, masking the CR-01 bug described above.

**Fix:** Use an explicit null/undefined check to distinguish "key is absent" from "key has a falsy value":
```typescript
.filter(k => {
  const v = (this.jobDetail!.metadata_ as any)[k];
  return v !== null && v !== undefined && v !== '';
})
```

### WR-03: `copyJobId` and `copyTraceback` swallow clipboard errors silently

**File:** `frontend/src/app/features/configuration/pages/job-monitor/job-detail-panel/job-detail-panel.component.ts:329-337`

**Issue:** Both clipboard methods call `navigator.clipboard.writeText(...).then(...)` without a `.catch()`. In non-HTTPS contexts (e.g. staging with HTTP), or when the browser denies clipboard permission, the rejected promise is unhandled. Angular does not catch unhandled promise rejections from imperative code — the user sees nothing and may believe the copy succeeded.

**Fix:**
```typescript
copyJobId(): void {
  navigator.clipboard.writeText(this.getJobId())
    .then(() => this.snackBar.open('Job ID copied.', '', { duration: 3000 }))
    .catch(() => this.snackBar.open('Copy failed — select and copy manually.', '', { duration: 4000 }));
}

copyTraceback(): void {
  navigator.clipboard.writeText(this.fullTraceback)
    .then(() => this.snackBar.open('Traceback copied.', '', { duration: 3000 }))
    .catch(() => this.snackBar.open('Copy failed — select and copy manually.', '', { duration: 4000 }));
}
```

### WR-04: Test for `brainsuite_job_id` metadata update is effectively a no-op — the assertion branch is never exercised

**File:** `backend/tests/services/test_instrumentation.py:501-518`

**Issue:** `test_scoring_output_schema` asserts on the `brainsuite_job_id` metadata update only `IF` any `update_background_job` calls with a `metadata` kwarg exist (lines 506-518). Because `_process_asset` is called with unmocked BrainSuite HTTP dependencies, it raises before ever reaching the `update_background_job(bg_job_id, metadata={"brainsuite_job_id": ...})` call at `scoring_job.py:519-523`. In practice, `update_metadata_calls` is always empty, the `for` loop body never executes, and the test passes unconditionally regardless of whether INSTR-05 is implemented. The comment at lines 507-512 acknowledges this but frames it as acceptable — it is not: this test provides zero protection for the phase's primary regression target.

**Fix:** Mock the BrainSuite submission and poll paths so the full happy path through `_process_asset` is exercised, or add a dedicated unit test that calls `update_background_job` directly with `metadata={"brainsuite_job_id": "test-id"}` and asserts the key is persisted:
```python
@pytest.mark.asyncio
async def test_scoring_metadata_brainsuite_job_id_persisted():
    """INSTR-05: update_background_job with metadata={'brainsuite_job_id': ...} merges the key."""
    from app.services.sync.job_tracker import update_background_job

    job_id = uuid.uuid4()
    mock_job = MagicMock()
    mock_job.metadata_ = {"asset_id": "abc", "creative_score_result_id": "def"}
    mock_job.status = "RUNNING"

    mock_db = AsyncMock()
    mock_db.get = AsyncMock(return_value=mock_job)
    mock_db.add = MagicMock()
    mock_db.commit = AsyncMock()

    with patch("app.services.sync.job_tracker.get_session_factory",
               _make_mock_session_factory(mock_db)):
        await update_background_job(job_id, metadata={"brainsuite_job_id": "bs-job-xyz"})

    assert mock_job.metadata_.get("brainsuite_job_id") == "bs-job-xyz", (
        "INSTR-05: brainsuite_job_id must be merged into metadata_"
    )
    # Existing keys must survive the merge
    assert mock_job.metadata_.get("asset_id") == "abc"
```

### IN-01: `get_redis()` is called inside the try block for SSE publish, creating a new singleton on every `job_tracker` import path

**File:** `backend/app/services/sync/job_tracker.py:62, 125`

**Issue:** `get_redis()` is a lazy singleton getter that creates the Redis client on first call. Calling it inside both `create_background_job` and `update_background_job` means the first invocation that hits the SSE publish block initialises the singleton. If Redis is unavailable at startup and `get_redis()` itself raises before `publish`, the `except Exception` block catches it correctly — so this is not a bug. However, calling `get_redis()` twice per helper (once per publish path) doubles the singleton-check overhead per job operation. Minor.

**Fix:** Cache the client at module import time or accept the negligible overhead — no action required unless Redis initialisation has side effects that should be isolated.

### IN-02: `datetime.utcnow()` used in `job_tracker.py` while `scoring_job.py` uses `datetime.now(timezone.utc)` — inconsistent timezone handling

**File:** `backend/app/services/sync/job_tracker.py:54, 118`

**Issue:** `started_at` and `ended_at` in `job_tracker.py` are set with `datetime.utcnow()` (naive UTC), while `scoring_job.py` consistently uses `datetime.now(timezone.utc)` (aware UTC). The `BackgroundJob` model declares both columns as `DateTime(timezone=True)`. PostgreSQL will store both correctly, but mixing aware and naive datetimes within the same application is a latent source of comparison bugs (e.g. `ended_at - started_at` raises `TypeError` if one is naive and the other is aware).

**Fix:** Standardise on `datetime.now(timezone.utc)` throughout:
```python
# job_tracker.py line 54
started_at=datetime.now(timezone.utc),

# job_tracker.py line 118
job.ended_at = datetime.now(timezone.utc)
```
Also add `from datetime import datetime, timezone` to the imports (currently only `datetime` is imported).
